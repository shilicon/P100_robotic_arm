CHAPTER 01

项目概述

Project Overview

项目将搭载 AMD Ryzen AI P100 的研华 MIO-5380 作为本地 AI 计算主机，与 RIG-ARM 桌面机械臂式交互机器人协同工作，实现语音理解、语言生成和受控的物理动作。

#1.1 项目目标与技术范围

本项目聚焦一个可运行、可测量的端侧物理 AI 系统：在本地完成语音识别（ASR）、语言模型（LLM）推理与语音合成（TTS），通过兼容服务接口与机器人固件连接。机器人承担唤醒、音频采集、屏幕反馈与机械运动的具体执行。

项目并不包含机器人底盘行走、自主导航或将舵机闭环控制交给大模型。现有控制器继续负责执行状态、约束和运动控制。

CHAPTER 02

硬件平台

Hardware Platform

从 P100 计算主机到 ESP32-S3 机器人控制器，整个系统采用计算与动作执行分工的硬件组织方式。

#2.1 AMD Ryzen AI P100

P100 在本项目中提供 CPU、集成 Radeon 890M GPU 和 XDNA 2 NPU 三类计算资源。CPU 运行语音识别、语音合成和服务协调；NPU 运行经过 AMD 适配的语言模型；集成 GPU 用于 Hybrid 推理与独立矩阵计算对照测试。

计算资源项目中使用方式注意事项
CPUSenseVoice int8、Huihui TTS、Python 服务、请求调度模型前向计算使用 NPU 不代表整个应用不使用 CPU
AMD XDNA 2 NPUQwen3-8B Full Fusion NPU-only需要相容的模型包、驱动、运行时及执行后端
Radeon 890M GPUHybrid Decode 与 DirectML MatMul 测试基础 GPU MatMul 吞吐不等于任意 AI 模型的吞吐

#2.2 研华 MIO-5380 主板

本地计算端采用研华 MIO-5380 开发板，装配 AMD Ryzen AI P100，配备 64 GB DDR5-5600（32 GB × 2）内存。板卡负责运行本地模型、接口服务和测试工具，也是与机器人之间的本地网络通信端点。

#2.3 RIG-ARM 机器人

组成设备 / 配置系统职责
主控ESP32-S3音频设备管理、状态控制、运动执行
输入麦克风、摄像头、语音唤醒获取声音和设备输入；视觉理解尚未部署
输出扬声器、屏幕播放合成语音与显示文字或状态
动作机构桌面固定底座、多轴动作点头、转头、鞠躬、摆动和已定义的动作工具

项目使用已有的 RIG-ARM 机器人，主要工作集中在本地模型部署、协议适配与交互流程优化；不会将其解释为拥有自主移动能力的机器人平台。

#3.3 工具调用与动作控制

以“向右转 20 度”为例，本地程序识别方向、角度与动作轴，校验有效范围后，向机器人返回对应动作工具。该项目资料给出的示例工具为 self_arm_yaw，参数 yaw=-20。工具语义中的正负方向由当前协议定义，不能脱离轴定义解释。

YAML
# 动作调用的文档化示例（非原始网络抓包）
tool: self_arm_yaw
arguments:
  yaw: -20

程序对工具名称、参数类型、方向与取值范围进行检查。对于明确动作口令可优先由规则处理，模型负责更灵活的语言理解。

#3.4 服务接口

用途路径协议与数据
实时 ASR/api-ws/v1/realtimeWebSocket；JSON + Base64 PCM
LLM 对话/v1/chat/completionsHTTP；Chat Completions 兼容接口，支持 SSE
实时 TTS/api-ws/v1/inference/WebSocket；文本任务 + 二进制 PCM
TTS 调试/v1/audio/speechHTTP；返回 PCM 或 WAV
ASR 调试/local/asrHTTP；输入 PCM、返回识别文本
健康检查/health返回模型、运行设备和配置信息

当前接口侧使用 16 kHz、单声道、16-bit PCM。健康接口返回的运行设备标签不能单独作为“模型真正运行在 NPU”这一结论的充分证据。

#3.5 流式处理与可靠性

  • 语音识别结合 VAD 判断一句话的结束时机，减少不必要的静默等待。
  • 语言模型分段输出；第一句形成后即可进入 TTS，后续文字继续生成。
  • 取消播放时停止待发音频；清空录音后不返回过期识别结果。
  • 模型推理使用独立工作进程或队列，避免阻塞网络服务与音频任务。
CHAPTER 04

AMD NPU 运行大语言模型

NPU Software Stack & Runtime

本章说明模型如何从开源权重变成可在 Ryzen AI NPU 上执行的部署资源，以及如何确认真实硬件参与了推理。

#4.1 Ryzen AI 软件栈

应用层机器人服务 / Python API提示词、动作工具、ASR / TTS
生成运行时ONNX Runtime GenAI（OGA）token 生成、KV cache、生成控制
设备执行RyzenAI Backend / 优化算子执行模式、算子调度、后处理资源
驱动层AMD NPU 驱动 / XRT设备上下文、硬件任务提交
硬件层XDNA 2 NPU在 P100 上执行模型计算

Qwen3 基础模型来自 Qwen，ONNX Runtime GenAI 是微软开源项目；AMD 提供针对 Ryzen AI 的模型适配、量化工具、运行后端、预优化模型包和诊断工具。该项目采用 AMD 发布的模型包，主要实现机器人场景的上层集成。

#4.2 从通用模型到 NPU 模型包

当前官方 Qwen3-8B NPU 4K 模型卡使用 AWQ、Group 128、Asymmetric、UINT4 权重与 BFP16 激活等配置。本项目直接部署 AMD 已制作的模型包，并未重新执行原始模型量化。

术语含义作用
AWQActivation-aware Weight Quantization通过激活信息指导权重量化，控制质量损失
Group 128以 128 个元素为粒度共享量化参数精度、元数据开销和执行方式之间的折中
Asymmetric允许偏移项的非对称映射适配数值分布
UINT4 Weights无符号 4 位权重降低模型存储及传输开销
BFP16 ActivationsBlock Floating Point 16 激活表示与硬件部署适配的分块浮点格式
i
术语区别

BFP16（Block Floating Point）与 BF16（bfloat16）不同。模型文件使用 ONNX 格式，也不自动意味着可在 AMD NPU 上运行；仍取决于模型、算子、后端、驱动及版本匹配。

#4.3 OGA 生成循环与后端执行

LLM 推理包含读取输入上下文的 Prefill 和逐 token 输出的 Decode。OGA 负责生成过程、分词与缓存，RyzenAI 后端将支持的计算提交给 NPU；CPU 仍负责应用控制与任务协调。

Python（原理示意，省略异常与取消逻辑）
import onnxruntime_genai as og

model = og.Model(model_directory)
tokenizer = og.Tokenizer(model)
input_tokens = tokenizer.encode(formatted_prompt)

params = og.GeneratorParams(model)
params.set_search_options(
    max_length=len(input_tokens) + output_limit,
    do_sample=False,
)

generator = og.Generator(model, params)
generator.append_tokens(input_tokens)
while not generator.is_done():
    generator.generate_next_token()
    token_id = generator.get_next_tokens()[0]
    # 将 token 解码为文字并交给流式输出流程

del generator

本机 OGA 运行环境包含 onnxruntime-genai.dll、onnxruntime_providers_ryzenai.dll、dyn_dispatch_core.dll、dyn_bins.dll 等配套组件。当前配置使用的执行后端名称是 RyzenAI；不要将其他 Vitis AI 示例中的 Provider 配置直接替换到这一路径。

#4.4 NPU-only 与 Hybrid 执行模式

模式PrefillDecode上下文范围 / 定位
NPU Full FusionNPUNPU当前 8B 包：输入 + 输出最多 4096 token
NPU Token FusionNPUNPU对应长上下文模型包最高 16K，用于长上下文对照
NPU + GPU HybridNPU集成 GPU取决于模型包与配置，不能一概视为 4K

TTFT（首 token 延迟）包含输入处理及初始化等开销；Decode token/s 描述后续输出速度。Hybrid 在专项 Benchmark 中可提高 Decode 速度，但并不保证每一种机器人真实请求、输入长度和模型版本都更快。

#4.7 自行准备其他模型的边界

模型适配包含检查架构支持、量化校准、OGA 导出、AMD 执行模式后处理，以及目标设备上的结果验证。官方工具不意味着“任意 PyTorch、ONNX 或 GGUF 模型都能一键转换到 NPU”。

Shell（官方流程示意）
# 以下仅为 AMD 文档中的命令形式，本项目未重新制作当前模型包
model_generate --npu --full_fusion \
  --input <quantized_model_path> --output <output_dir>

model_generate --npu --token_fusion \
  --input <quantized_model_path> --output <output_dir> \
  --extra_options max_seq_len=16384

model_generate --hybrid \
  --input <quantized_model_path> --output <output_dir>

量化可能需要单独的 Linux / GPU 环境。对新增算子形状或修改过的模型架构，还需额外检查预编译算子和编译流程的支持状态。

CHAPTER 05

大模型选型与动作调用测试

Model Selection

机器人动作工具调用需要模型具备足够好的语义判断与参数生成能力；仅比较文本生成速度并不足以解释实际任务质量。

#5.1 测试目标与方法

测试集中共 20 个问题，其中 12 个明确要求动作工具，其余覆盖普通对话、否定表达、参数范围、状态描述和能力边界。评测只检查生成文本及工具调用的名称、类型、方向、范围和状态语义，不会真的驱动机械动作。

对比模型统一使用既定工具集；Phi-4-mini 使用与自身匹配的工具模板。此测试侧重本项目任务，不是通用语言模型榜单。

#5.3 测试结果与选型

  • 较小模型的生成更快，但工具名、方向、参数类型、范围及语义判断的错误更多。
  • Qwen3-8B NPU 4K 在所选六组结果中达到 10 / 12 的动作调用通过数，是当前主语言模型基础。
  • Hybrid 运行模式不能自动修复动作语义问题；优化还需要依靠规则、提示词与应用级参数校验。

#6.5 功耗、能量与温度测量

通过 Windows Win32_PerfRawData_PowerMeterCounter_EnergyMeter 的组件级累计 Energy 计数器差分积分，计算 GPU、NPU、APU 与 RAPL Package 等的平均功耗。功耗采样在独立进程执行，以减少 Python 生成循环阻塞采样的影响。

Python（计数器换算）
energy_joule = (Energy_end - Energy_start) / 2**28
average_watt = energy_joule / elapsed_seconds

本轮空闲基线约为 RAPL Package 20.41 W、GPU 2.34 W、NPU 0 W。采样计划间隔 0.2 秒，实际由于 WMI 查询耗时通常约 0.6–0.7 秒，适于平均功耗对比，不适于捕捉微秒级功耗尖峰。

最高约 34.56°C 的读数来自 ACPI / EC 热区，不能当作 CPU Tctl / Tdie、GPU Hotspot 或 NPU Die 的直接温度。

i
测量限制

这些是 SoC / 组件估算值，不是墙上插座功率；能量采样窗口也略短于完整推理请求，不能直接视为整机精确能耗。

#6.6 测试结论与适用范围

  • NPU 内置 GEMM、GPU DirectML MatMul 和真实 LLM 推理属于三类不同测试，不宜用一个 TOPS / FLOPS 数字概括全部负载。
  • 本轮 Hybrid 在固定解码任务中更快，但 GPU 和 Package 功耗更高；NPU-only 是目前机器人应用选择的执行路径。
  • xrt-smi 能核验 NPU context 提交与完成，但上下文任务计数并不等于 token 数。
  • 短时间温度测试没有观察到明显热降速，但不足以证明长时间重负载的持续温度或稳定性。

#6.7 Benchmark 复现方法与数据文件

项目测试使用 work/npu_gpu_power_benchmark.py，并在输出目录中保存 JSON 汇总、逐样本 CSV、NPU validate 报告和 context 记录。实际执行需以仓库中的脚本路径、依赖和当前主机环境为准。

CHAPTER 07

机器人应用工程实现

Implementation Details

AMD NPU 软件栈提供了模型推理能力，但可靠的机器人交互还依赖音频管线、接口适配、工具约束和任务生命周期管理。

#7.1 实时语音链路

  • 保留机器人设备侧的唤醒和收音能力，通过 WebSocket 传递音频。
  • 使用 Silero VAD 检测语音结束，SenseVoice int8 在 CPU 上完成中文识别。
  • 文字输出按句分段送往 Huihui TTS，已生成的第一句可以提前进入播报。
  • 支持停止待发音频，并清除取消请求后可能迟到的旧识别结果。

#7.2 LLM 服务封装

项目使用 OGA Python API 装载 AMD 适配的 Qwen3-8B 模型。应用负责聊天模板、提示词精简、历史裁剪、上下文上限、生成参数及输出解析；推理工作进程独立于网络请求处理。

现有部署直接调用 OGA，不需要经由 Lemonade Server。Lemonade 可以作为更高层的模型服务封装，但替换模型服务并不会自动完成机器人协议、ASR / TTS、工具调用或执行状态适配。

#7.3 动作工具的可靠性设计

层次责任示例
意图识别理解用户希望机器人完成的动作“向右转 20 度”
工具解析选择允许的工具及其参数self_arm_yaw / yaw=-20
规则与参数检查验证方向、角度、类型、状态和范围超出范围的调用不得直接执行

#7.4 延迟与流程优化

缩短端侧交互等待时间不只涉及更换更快的模型。项目已使用输入精简、明确口令规则、工作进程分离、流式文字输出和逐句语音合成等方案，降低用户感知的等待。

工程优化应分别记录识别结束、首 token、完整文本生成、首段语音开始和动作真正完成等时间点。不同阶段的指标不能只用一个“响应速度”混在一起。

#7.5 可靠性与已知问题

  • 本地工具在某些条件下仍可能选错动作、误解方向或生成不准确的状态描述。
  • 完整工具推理实测约 21 秒的记录说明复杂请求仍有明显延迟空间。
  • 语音识别和合成均部署于 CPU；目前并未证明在真实现场噪声下识别准确性得到提升。
  • 慧慧 TTS 的声音与原云端音色不同，项目尚未完成音色克隆。
